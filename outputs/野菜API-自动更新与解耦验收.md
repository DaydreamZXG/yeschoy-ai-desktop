# 野菜 API 完整 UX、接入、自动更新与解耦验收审计

审计版本：0.4.14

审计对象：野菜 API 桌面助手；macOS 与 Windows；Codex Desktop、Claude Desktop、Claude Code、Pi、DSH web、Hermes、OpenClaw。

审计目标：让第一次接触本地 AI 工具的用户完成“发现或安装应用 → 选模型和计费分组 → 一键接入 → 日常打开 → 调整或恢复 → 野菜自身更新”，同时任何失败都不能锁死客户端、破坏用户原设置或串到其他功能。

## 1. 总结结论

此前最严重的问题不是单个按钮或文案，而是边界混在一起：应用发现、退出第三方应用、写配置、等待模型回复、启动应用、第三方安装、野菜自身更新共用过多状态。一个慢请求或上游错误会让用户误以为整个客户端卡死，也使“本地配置已成功”被错误回滚。

0.4.14 将产品收敛为三条互不依赖的链路：

1. **应用接入**只负责发现、必要时正常退出桌面应用、原子写入与读回设置、启动本地桥和重新打开；不发送收费模型探针。
2. **第三方应用安装**只负责 Codex、Claude 等应用的来源解析、下载、校验、安装和安装状态；不决定模型、线路或野菜版本。
3. **野菜自身更新**只检查固定更新频道、下载并校验野菜更新包、安全停止本地运行时、安装并重启；不读取账号、模型、计费分组、应用接入设置或第三方安装任务。

自动更新的代码、固定域名、发布器、公钥、Windows 更新包工作流和设置页交互已经建立。更新频道采用失败关闭：只有 macOS 与 Windows 的完整更新构件都存在时才发布清单；否则 `stable.json` 返回空的 204，客户端继续正常使用，其他功能不受影响。

## 2. 审计依据与限制

本次结论来自当前源码、组件与原生单元测试、治理验收、生产构建、下载源公开探测、Tauri 更新器固定版本的实际实现，以及 macOS/Windows 发布脚本。截图或 AI 自述不作为“已走野菜中转”“已安装成功”或“更新成功”的证据。

以下事项必须区分：

- 编译通过不等于真实 Windows 安装和退出行为通过。
- 更新包签名正确不等于 macOS 公证、Gatekeeper 或 Windows SmartScreen 通过。
- 本地设置写入成功不等于上游模型当前可用。
- 线路可达不等于账号、配额、模型或供应商健康。
- 0.4.13 及更早版本没有更新器，无法被服务器远程补装；首次升级到 0.4.14 仍需安装一次新包。

## 4. 面向小白用户的目标流程

### 4.1 第一次使用

1. 野菜自动检查已安装应用；不启动第三方 CLI，不因版本号不同直接判定“不支持”。
2. 未安装时显示“安装并接入”；已安装时直接进入模型、计费分组和线路选择。
3. 用户确认前不改任何设置；需要退出 Codex Desktop 或 Claude Desktop 时，先提醒保存工作。
4. 用户确认后请求目标应用正常退出，原子保存原始字节，再写入并读回野菜配置。
5. 配置成功即显示“打开使用”；不会用一条收费模型消息充当接入门禁。
6. 第一次真实消息的转发模型、目标应用、线路和结果进入“最近连接结果”，用于判断是否真正经过野菜。

### 4.2 日常使用与换模型

- “打开使用”只启动已有配置，不重写文件。
- 常用模型可有多个，每个模型保存一个明确计费分组；应用内可直接切换已下发模型。
- 新增模型、修改默认模型或调整分组时才使用“更新接入设置”。
- “恢复原设置”恢复首次接入前的用户字节，不强制用户继续使用野菜。

### 4.3 失败恢复

- 上游 5xx、配额或模型拒绝：保留本地接入，提示重试或换线路，不伪装成本地配置失败。
- 应用拒绝正常退出：停止写入，不强杀，不改设置。
- 写入中断：恢复原始内容和密钥引用；若野菜曾正常退出目标应用，则尝试重新打开。
- 启动失败：保留已验证配置，给出重试和接入详情；不会无限显示 pending。
- 更新服务器不可达：只把更新状态标为暂时不可用，不阻塞接入、安装、诊断、账单或退出。

## 5. 七类应用生命周期规则

| 类型 | 应用 | 接入/调整时 | 打开使用时 | 不做什么 |
| --- | --- | --- | --- | --- |
| 桌面应用 | Codex Desktop、Claude Desktop | 若正在运行，提示保存并请求正常退出；写入成功后重开 | 启动应用和本地桥 | 不强杀，不依赖 AI 自我介绍判断模型 |
| 终端 Agent | Claude Code、Pi、Hermes、OpenClaw | 不结束现有终端；新会话读取新设置 | 打开新终端会话 | 不打断当前任务 |
| 浏览器工作台 | DSH web | 保存野菜拥有的配置和运行时信息 | 复用或启动本地服务并打开浏览器 | 不套用桌面进程退出规则，不接管用户其他 DSH 进程 |

适配器仍按目标应用分别实现，因为配置文件、启动方式和模型能力确实不同；但发现、事务、恢复、超时、退出协调、密钥引用和用户反馈必须复用同一套公共机制。这里的“解耦”不是复制七套流程，而是公共内核与应用差异分层。

## 6. 解耦后的责任边界

| 域 | 唯一职责 | 自有状态/锁 | 明确禁止依赖 |
| --- | --- | --- | --- |
| 应用发现 | 只读识别受支持应用与精确安装身份 | 发现缓存 | 账号、模型请求、更新频道 |
| 应用接入 | 备份、配置事务、读回验证、恢复 | 接入事务与目标应用锁 | 野菜更新状态、第三方下载任务 |
| 本地桥 | 把目标应用协议转换到用户选定的模型和分组 | 路由快照与本地凭据引用 | UI 文案、安装来源 |
| 第三方安装 | 来源解析、下载、校验、安装、重扫 | 安装任务锁 | 模型选择、野菜更新清单 |
| 野菜自身更新 | 固定频道检查、下载校验、关停、替换、重启 | 独立更新锁与候选版本 | 账号、计费、接入锁、第三方安装目录 |
| 账号与账单 | 登录投影、余额、真实用量和价格比较 | 会话世代 | 本机路径、更新私钥 |
| 诊断 | 两条固定线路的只读可达性与最近请求事实 | 只读结果 | 付费模型探针、配置写入 |

更新器在原生层只有一个封闭命令，渲染器不能传入更新 URL、公钥、文件路径或安装命令。客户端仅内置公钥；私钥只存在于发布环境。更新下载完成并通过校验前，不请求退出野菜；准备替换时复用统一关停协调器，但不复用接入或安装锁。

## 7. 自动更新状态机与用户反馈

`idle → checking → current | available | unavailable`

`available → downloading → restarting`

`checking | downloading | restarting → failed` 只表示更新链路失败，不改变其他产品状态。

| 状态 | 用户看到什么 | 可执行动作 |
| --- | --- | --- |
| idle/checking | 设置页显示后台检查，不弹全局错误 | 继续使用所有功能 |
| current | 已是最新版与当前版本 | 重新检查 |
| available | 非模态更新提示、版本和说明 | 更新并重启、稍后处理 |
| downloading | 下载进度；野菜保持运行 | 等待；其他非冲突页面仍可浏览 |
| restarting | 正在安全结束本地运行时并重启 | 不重复触发安装 |
| unavailable | 更新服务暂时无响应 | 重新检查；不影响其他功能 |
| failed | 安装未完成或安全校验失败 | 重试检查；当前版本重新启动并保留配置 |

发布端要求 macOS 通用包同时覆盖 Intel 与 Apple Silicon，并要求 Windows x64 包齐全。构件先写入不可变版本目录，最后原子发布 `stable.json`；同版本重放、降级、缺失平台、空校验文本、路径穿越、符号链接和异字节覆盖全部失败关闭。撤回频道只移动清单，不删除历史构件，也不改变第三方应用下载状态。

## 8. UX 启发式审计

### 状态可见性

- 长任务均有阶段、当前动作和有限等待时间。
- 后台刷新不清空上一份可用信息。
- “本地接入成功”和“最近上游请求失败”分区显示，不互相覆盖。

### 用户控制与可逆性

- 所有写入前都可取消；运行中的桌面应用需要显式确认。
- 已接入后始终保留“更新接入设置”和“恢复原设置”。
- 关闭窗口可选后台运行或完全退出；完全退出不删除设置。
- 更新提示非模态，除用户主动安装外不抢占工作。

### 一致性与识别优先

- 模型显示用户名称与完整 ID，不显示内部上游采购信息。
- 大陆优化与全球加速均明确说明适用网络，并强调不改变倍率。
- 桌面、终端、浏览器三类应用采用一致动作层级，但生命周期说明不同。

### 防错与恢复

- 不因普通未来版本直接拒绝适配；依赖可验证的能力和配置结构。
- 不把一次模型回复、AI 自我介绍或线路 TCP 可达当作完整接入成功。
- 原始配置只记录一次基线，重复接入不要求先恢复，也不覆盖恢复点。
- 所有跨进程修改使用有界等待和失败回滚；不提供无期限旋转状态。

### 可访问性与小窗口

- 关键状态使用文字和图标双重表达，不只依赖颜色。
- 动态更新提示使用 `aria-live`，进度使用原生 `progress`。
- 主动作与次动作在窄侧栏保持完整宽度；更新提示在小窗口改为纵向排列。
- 发布前仍需在 Windows 系统缩放 125%/150%、键盘导航和屏幕阅读器下做人工验收。

## 10. 发布与回退清单

发布者必须完成：

1. 三处版本一致：`package.json`、Tauri 配置、Cargo 包版本。
2. 全量测试、类型检查、Rust 格式与 Clippy 通过。
3. Windows 生成 NSIS 安装程序、`.nsis.zip` 和对应更新校验文件。
4. macOS 通用应用完成 Developer ID、强化运行时、公证、票据装订，再生成 `.app.tar.gz` 和对应更新校验文件。
5. 两个平台构件哈希留档；服务器发布器一次性接收三个目标。
6. 发布后从公网读取清单，逐项核对 HTTPS URL、版本、平台、签名文本和不可变缓存头。
7. 若发现问题，立即执行频道 disable；旧客户端继续使用当前版本，第三方下载源保持不变。

不得执行：把更新私钥提交到仓库或服务器公开目录；只发布单个平台；使用同版本覆盖不同字节；把失败的更新检查升级成应用接入门禁；为修复更新而重写用户 Codex、Claude、Pi 或 DSH 配置。

## 11. 接手者最短检查路径

1. 先读 `src/update/` 与 `src-tauri/src/app_update.rs`，确认更新命令仍是封闭输入。
2. 再读 `deploy/self-update/`，确认构件优先、清单最后和可撤回语义未被破坏。
3. 对接入问题从公共事务/生命周期层定位，再检查目标适配器；不要为某一个应用复制整条流程。
4. 对“连上但没走野菜”的判断只看最近本地桥记录、实际转发模型和服务端账单，不看界面模型简称或 AI 自述。
5. 修改任何写入、退出、安装或更新行为前，新增失败、取消、超时、重复点击和恢复场景。

## 12. 发布判断

代码层可进入 0.4.14 候选包阶段；自动更新频道只能在完整签名构件与公网复核通过后启用。首个更新器版本发布后，仍不能把“更新框架存在”写成“跨版本升级已真机通过”；该结论必须由 0.4.14 → 0.4.15 的三平台证据关闭。

## 13. OAuth 2.0 + PKCE v1.1 契约审计

### 13.1 当前事实

技术同事提供的《New API 客户端 OAuth 2.0 + PKCE 接口文档（Loopback 随机端口版）》是一份待实现的对接契约，不是现网能力证明。2026-09-07 的无凭证只读探测结果如下：

- `https://yeschoy.com/api/desktop/v2/bootstrap` 与 `https://api.yeschoy.com/api/desktop/v2/bootstrap` 均返回 schema 2、`desktop-integration-v2`，并声明当前设备授权可用。
- `POST https://yeschoy.com/api/oauth/token` 返回 404，说明新 Token Endpoint 尚未部署。
- `/api/oauth/authorize` 与 `/api/oauth/userinfo` 当前进入 New API 原有 OAuth provider 路由并返回 `Unknown OAuth provider`，并非文档定义的桌面客户端接口。
- 未携带凭证访问 `/v1/models` 返回 401，只能证明该资源受保护，不能证明它已经接受新 OAuth Access Token。

因此 0.4.14 不能直接删除现有设备授权或强制切换到 PKCE，否则会把已部署的登录链路替换为不存在的接口。

### 13.2 正确迁移方式

账号认证采用兼容双栈，不通过试错请求猜测能力：

1. 服务端 bootstrap 新增明确的认证能力和契约版本，例如 `oauth_loopback_pkce_available`、授权源、资源源与支持的账号数据能力。
2. 客户端仅在服务端显式声明且契约校验通过时启用 loopback PKCE；否则继续使用当前 v2 设备授权。
3. OAuth 的 Token 与业务 API 源固定复用野菜服务，不跟随“大陆优化/全球加速”切换；浏览器授权确认页允许按客户端品牌使用一个编译时白名单域名。野菜版使用 `yeschoy.com`，朋友定制版使用 `ai.yeschoy.io`。
4. 服务端必须明确 OAuth Token 是否同时可用于 `yeschoy.com` 和 `api.yeschoy.com` 的 `/v1/*`，以及它们是否共享 audience、会话撤销和鉴权缓存。
5. 客户端继续复用现有安全存储、刷新互斥、账号世代和退出协调，但新增独立的 loopback listener、PKCE 临时上下文与表单编码网络边界。
6. 默认 scope 只申请 `profile api offline_access`；不申请工具密钥管理或后台管理权限。设备管理 `sessions` 属于可选高权限，只有真正提供设备管理界面时才单独申请。

### 13.3 与应用接入的解耦要求

OAuth Access Token 最长仅一小时，不能像长期 API Key 一样直接写入 Codex、Claude、Pi、DSH、Hermes 或 OpenClaw 配置。正确边界是：第三方应用只连接野菜本机桥；本机桥从账号会话模块取得短期 Access Token，并由账号模块串行刷新。退出登录只撤销账号会话并停止新的远端请求，不改写或删除用户原始应用配置。

用户已确认新 OAuth 契约的目标就是缩小原桌面接口权限。新的 Access Token 不得继承当前 bootstrap 中的 `tool_keys_manage` 能力，也不得调用后台管理、用户列表、其他用户账单或上游密钥接口。迁移期间需明确以下其一：

- 仅给仍使用 v2 设备授权的旧客户端保留工具密钥兼容层；或
- 所有目标应用统一经本机桥转发，由桥使用 OAuth Token，且补齐用量、定价、余额和模型能力接口。

文档目前只定义 `userinfo`、`/v1/models` 与模型调用，没有覆盖现有客户端使用的用量记录、价格、节省金额和工具密钥管理能力；这些缺口关闭前不能宣称账号功能已完整迁移。

### 13.4 PKCE 实现门禁

- 必须先绑定 `127.0.0.1:0` 并持续持有 listener，再打开系统浏览器；不接受 `localhost`、`0.0.0.0`、固定端口或自定义 URL Scheme。
- `state` 与 verifier 每次独立生成；只接受 S256；完整 redirect URI（含实际端口）在授权和换码时完全一致。
- callback 严格限制 GET、Host、路径、单值关键参数和一次原子领取；错误 state、favicon 或陌生请求不能毁掉合法等待流程。
- Token Endpoint 固定 HTTPS、禁止跨地址重定向；回调页不回显任何敏感值，也不加载外部资源。
- Refresh Token 使用安全存储并旋转；同一会话 singleflight；响应结果不确定时不盲目重放一次性 code 或 refresh token。
- SSE 已开始、已产生工具调用或执行结果不确定时，不自动重放模型请求，避免重复计费和副作用。
- 日志和错误上报过滤 Authorization、code、verifier、Token、完整 callback URL 以及 Token 请求/响应体。

### 13.5 发布门禁调整

PKCE 客户端可以先开发为未启用的兼容分支并完成单元测试，但在服务端提供可验证的能力声明、两个资源线路的 Token 语义和完整联调环境前，不得替换当前生产登录。正式启用还必须完成文档第 22 节全部联调场景，并增加“旧设备授权仍可回退”“切换网络线路不退出账号”“OAuth 退出不破坏应用恢复点”“定制授权页不能改变 Token/API 源”四项客户端集成验收。

### 13.6 `ai.yeschoy.io` 定制边界

用户确认 `ai.yeschoy.io` 只用于朋友定制客户端在系统浏览器中展示登录与授权确认页面；不是一套新的 API、账号、模型、计费、线路、本地桥或更新服务。其他能力继续复用野菜现有实现。

实现上只增加受控的产品参数：

```text
authorization_page_origin = https://ai.yeschoy.io
token_api_origin          = https://yeschoy.com
resource_api_origins      = 继续使用野菜既有线路
redirect_uri              = http://127.0.0.1:{动态端口}/oauth/callback
```

当前设备授权兼容期对应的构建变量为 `YESCHOY_AUTHORIZATION_PAGE_ORIGIN`。未设置时固定为 `https://yeschoy.com`；朋友定制构建只允许精确值 `https://ai.yeschoy.io`。客户端仍先验证服务端返回的野菜授权结果，再使用已验证的 `user_code` 在本地重建 `/desktop-authorize` 浏览器地址，服务端响应不能选择或覆盖该 Origin。

该参数必须在构建时写入并按精确 HTTPS Origin 白名单校验，不能做成允许用户填写任意网址的设置，也不能让授权页返回的参数覆盖 Token Endpoint。授权码须由同一野菜 OAuth 服务签发并能在固定 Token Endpoint 兑换；定制域名只改变浏览器页面入口和品牌展示。

因此无需复制整套客户端或分叉七个应用适配器。共享 PKCE、本机回调、安全存储、刷新、本地桥和更新代码；朋友版只覆盖授权页 Origin 及未来明确提供的名称、图标和文案资产。若将来需要独立账号体系、计费或更新源，再建立新的产品变体契约，不能从这次“只换授权页域名”推断出来。

### 13.7 客户端先行准备结果

客户端侧已经完成可编译、但默认休眠的 PKCE 预埋；不需要等待服务端部署才能完成客户端开发。当前实现已经覆盖随机端口 IPv4 loopback listener、独立 state/verifier、PKCE S256、两个授权页面 Origin 白名单、固定野菜 Token/UserInfo/Revoke Endpoint、严格且不误消费的 callback 校验、一次原子领取、表单编码、受限 Token 响应解析、取消与超时。凭证对象没有 `Debug` 派生，回调响应不包含 code、state 或 Token。

该模块只被 Rust 编译器纳入构建，没有 Tauri command、前端入口或当前账号模块调用者，因此现有 `/api/desktop/v2/*` 设备授权、会话存储、工具密钥、计费分组以及 Codex、Claude、Pi、DSH、Hermes、OpenClaw 等应用接入逻辑均未改变。移除该模块即可回滚，不涉及数据迁移。

仍需服务端上线后关闭的不是“客户端能不能写”，而是两项真实联调事实：一是 bootstrap 如何明确声明 PKCE 能力并让客户端安全切换；二是窄权限 OAuth Bearer 如何选择计费分组并供所有本机桥调用，同时覆盖账号、余额、用量、定价和模型能力。两项契约冻结并部署前，生产登录继续走现有设备授权；不得用当前未部署接口做试错切换，也不得宣称 OAuth 已经可供用户使用。
