## 问题 A：`gpt pro纯真自建号池` 铸不出 key

### 为什么现在查不出根因

`tool_activation.rs` 的 `server_success()` 只返回 bool：

```rust
fn server_success(status: u16, value: &Value) -> bool {
    (200..300).contains(&status)
        && value.as_object().and_then(|o| o.get("success")).and_then(Value::as_bool) == Some(true)
}
```

new-api 失败时回的是 `{"success": false, "message": "..."}` —— **那句 message 就是答案**，
在这里被丢掉了。铸 key 这条路上五个不同的失败点全部塌成同一个 `server_unavailable`。

### 候选（按证据强度，全部未验证）

| 猜测 | 在哪一步炸 | 证据强度 |
| --- | --- | --- |
| **token 数量到上限** | `POST /api/token/` | 较强：`gpt` 是绑定列表里**最后一个**，前三个都成了；列表里已有 6 把 |
| **重复 / 同名冲突** | `POST /api/token/` | 中：该分组确实已有一把，但 DeepSeek Flash 重复了两把说明中转**允许**重复 |
| 账户对该分组没权限 | `POST /api/token/` | 弱：6 小时前还建成过 |
| 建完了读不回来 | `find_token_id(exact=true)` → `ok_or(ServerUnavailable)` | 未知 |
| 建完了取不到 key | `fetch_token_key` | 未知（这条会尝试 DELETE 掉刚建的） |

**「最后一个才失败」这条最值得追**：循环按绑定顺序逐个分组铸，
deepseek / gemini / glm 三个成了，gpt 是第四个。如果有账户级 token 上限，
表现就正好是这样。

### 要问中转技术人员的三个问题

1. **这个账户的 token 数量有上限吗？是多少？** 现在 6 把。
2. `POST /api/token/` 在 2026-09-20 22:43 前后对这个账户返回的 **`message` 原文**是什么？
3. 同一分组允许几把 token？重名（`name` 相同）会被拒吗？

## 问题 B：旧 token 不回收，在账户里堆积

`DeepSeek Flash` 两把并存，说明**退役逻辑没认出那把旧的**。

### 机制

`acquire_token_using` 找已有 token 时，`find_token_id(..., exact=false)` 会：

- 用 `owned_token` 按**名字前缀 + 分组**筛；
- 再用 `token_is_ours` 按**设备标识**筛：名字必须是 `<prefix>-<device8><nonce8>`，
  而 `device8` 要等于本机 `~/.yeschoy/device-id`（**本机实测 `dba3f940`**）；
- 选中一把复用，**其余的进 `retire_after_commit`**，接入提交后由
  `retire_superseded_tokens` 后台 DELETE。

日志里 **`tool_token_cleanup` 零命中** —— 而那把 2 小时前的还在。
所以它**根本没被排进退役队列**，也就是说上面某一道筛把它滤掉了。

### 候选

| 猜测 | 怎么验证 |
| --- | --- |
| 那把旧 token 的名字里是**别的设备号** | 看它的完整 `name`，比对 `dba3f940` |
| 用的是**旧命名**（`野菜API cx-<hash>`） | 看 `name` 前缀是 `野菜API Codex-` 还是 `野菜API cx-` |
| **分组哈希不同**（同名分组、不同 id） | 比对 `name` 里那 8 位 hex 与 `915eb5e2` 等 |

**一个问题就能定案**：那两把 `DeepSeek Flash` 的**完整 name 分别是什么**？

### 顺带：退役失败的日志分不出两种情况

`tool_token_cleanup` 零命中，既可能是「从没尝试退役」，也可能是「都成功了」——
现在的日志区分不了。补一条「尝试退役 N 把」的 info 就能分开。

## 给下一个工程师

### 要改的（按价值排）

1. **把中转的 `message` 记进日志**（问题 A 的唯一出路）。
   落点：`tool_activation.rs` 的 `acquire_token_using` 里三处 `server_success` 判断
   + `fetch_token_key`。

   两条硬约束：
   - **只进日志，不进界面。** 中转原话可能含账户信息，而且对用户没有可操作性
     （「这个分组没权限」要找的是客服，不是按钮）。
   - **别拿 message 当分支条件。** 那是自由文本，会变；判断仍然走 `success` 布尔。
     （这条踩过：`supported_endpoint_types` 已经判错过三次，同一个方向。）

2. **退役路径补一条 info 日志**（问题 B 的可观测性）。
   落点：`retire_superseded_tokens`，现在只在失败时 warn。

3. **「有模型没配上」要能持久看到**。现在 `skipped` 只活在 React 临时状态里：
   离开接入页再回来就没了，而列表还显示 4 个、实际写进去 3 个。
   方向是把它变成**连接状态的一部分**——`ToolConnection.models` 已经来自凭据，
   和用户的模型列表一比就知道少了谁，不需要新协议字段。

### 不要做的

- **不要加门禁**：不要因为某个分组曾经失败就把它从选择列表里灰掉。
  这条踩过三次（`supported_endpoint_types`），每次都是「把不知道当成不行」。
  失败是一次真实请求的结果，不是预测的依据。
- **不要为了去重去删中转上的 token**，除非确认那把是本机的。
  `token_is_ours` 那道设备筛是有来历的：没有它的时候，
  在第二台电脑上登录并选一组略有不同的模型，会**静默吊销第一台的 key**，
  那台机器随后开始无声失败。
