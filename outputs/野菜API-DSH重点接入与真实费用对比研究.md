# 野菜API：DSH 重点接入与真实费用对比

日期：2026-08-31。性质：只读研究与后续产品提案，不是已实现或已上线说明。

本次未访问生产服务器，未修改 NewAPI、第三方工具配置或密钥，未发起模型请求，未安装或启动 DSH。只修改本地研究记录和需求索引；既有 RU-014 的界面实现与冻结快照不变。

## 1. 已确认的方向与当前差距

- **用户确认**：DSH 很重要，需要重点核查接入；费用对比既要直观体现优惠，也要能被专业用户复核，不能虚构节省。
- **后续确认（DEC-058）**：用户接受从野菜API助手一键启动 DSH，再用浏览器打开其官方本机界面；首版不要求另做独立或嵌入式 DSH 窗口。此次确认仅解决打开方式，不代表适配完成或全部费用核算细则获批。
- **既有约定**：DSH 指 DeepSeek Harness，V1 只接 `web` profile；官网基准数值由 NewAPI 统一维护；比较汇率固定 `1 USD = 6.75 CNY`；服务器改造交给技术负责人。
- **代码现状**：首页重点展示 Claude/Codex 桌面应用，DSH 仍是次级命令行发现对象；`src/configuration/preview.ts` 仍有 `dsh_web_adapter_required`，没有可用的 DSH 自动配置器。`src/workbench/ModelsView.tsx` 和 `AccountView.tsx` 的价格、账单仍是明确不可用状态，不能展示真实节省金额。
- **本次不推断**：提高 DSH 优先级不自动撤销原来的“不单独阻止整个 V1 发布”决定，也不等于已允许捆绑第三方运行环境或把 DSH 页面接入客户端原生权限。

## 2. DSH 接入方向

### 2.1 已核查的官方能力

DSH 官方提供 `web` 可视界面，启动本地服务后由浏览器访问；不能将这个入口称为官方原生桌面安装器。官方 README 同时说明项目仍处于开发者预览阶段，支持范围必须绑定实际验证过的版本，而不是假定所有新版本都兼容。

本次固定核查源码提交 `0a53fb55bea101816fa226bb964ae2bed71c343b`。根 `package.json` 为 `0.1.2-alpha.2`，声明 Node `^22.19.0 || >=24.0.0`；这是源码要求，不是已验证的 npm 发布包或本机安装版本，旧文档的 `0.1.0-rc.6` 不能沿用为当前支持证据。

另一次只读查询显示 [npm 默认发布版本](https://registry.npmjs.org/@deepseek-ai%2Fdsh/latest) 当前是 `0.1.1-rc.2`，与上述源码不同。后续必须对选定发布包重新核查接口、校验产物和运行验证，不能直接使用 master 调研结果承诺默认安装版兼容。

自定义 provider 支持独立 ID、基础 URL、协议、凭据引用及模型列表；`llm-pi-ai` 的 `openai-completions` 配置提供了接 Chat 兼容接口的路径。`compat`、图片输入和推理格式是需要验证的声明，不会自动证明线路支持这些功能。选择默认模型也不等于强制替换所有已有会话的模型。

默认凭据存储仍是 `$DSH_HOME/.credentials.yaml`，而不是系统钥匙串；官方凭据扩展说明中的 keyring/helper/KMS provider 尚未随包提供。因此我们需要自己的适配，不能说是“现成安全接入”。

来源：[启动说明](https://github.com/deepseek-ai/deepseek-harness/blob/0a53fb55bea101816fa226bb964ae2bed71c343b/README.md)、[运行环境声明](https://github.com/deepseek-ai/deepseek-harness/blob/0a53fb55bea101816fa226bb964ae2bed71c343b/package.json)、[供应商配置](https://github.com/deepseek-ai/deepseek-harness/blob/0a53fb55bea101816fa226bb964ae2bed71c343b/docs/user/guide/providers.zh.md)、[凭据扩展契约](https://github.com/deepseek-ai/deepseek-harness/blob/0a53fb55bea101816fa226bb964ae2bed71c343b/packages/credentials/credentials/README.md)、[默认本地存储](https://github.com/deepseek-ai/deepseek-harness/blob/0a53fb55bea101816fa226bb964ae2bed71c343b/packages/credentials/credentials-local/README.md)。本节是源码/文档核查，不是本机启动测试。

### 2.2 面向用户的接入流程（打开方式已确认，实现待验证）

1. 主应用列表单列「DSH」，显示真实安装/运行状态，不让用户去“高级工具”找。
2. 用户选择野菜线路和真实模型 ID；只推荐已通过该版本、协议和工具调用验证的组合。
3. 助手处理配置和密钥引用；用户不手填 API 地址或修改文件。
4. 点击「打开 DSH」，由助手启动经过验证的本地程序并打开其官方界面。
5. 启动失败、端口被占用、版本不支持、密钥不可用时说明下一步，不把“找到程序”显示成“接入成功”。

已确认首版复用 DSH 官方浏览器界面，不另做独立窗口。不能把具备项目文件/命令执行能力的 DSH 页面直接加载到拥有野菜账户、密钥或原生命令权限的主窗口。将来如需改为嵌入式窗口，须另行决定并验证隔离方案。

### 2.3 实现前的安全与兼容验证

- 使用两个既定 HTTPS 线路；准确的协议端点和模型配置由版本化适配器产生。是否支持某协议、流式输出、推理内容、工具调用及工具结果回传，需要实测，不能由模型名称推断。
- 密钥仍由系统凭据库保管，通过专用凭据提供器读取。不把野菜密钥写进 DSH 普通设置、`.env`、默认本地凭据文件、启动参数或日志。
- 凭据库主要解决秘密明文落盘，不自动隔离同一系统用户运行的工具或不可信插件；提供器仍需限制调用者和凭据范围，不能承诺“代理绝对读不到密钥”。
- 只管理野菜自己的 provider 和已确认的 web 配置范围，保留用户其他 provider、凭据和项目设置。不能以“替换整个凭据服务”实现接入，却丢失其他账户。
- 启动前明确运行环境来源、版本、下载校验、进程归属和退出行为；不执行未固定版本的在线安装脚本，不接管未知本地进程。
- 默认仅允许本机访问，核查 Host/Origin、会话认证、端口归属及打开的项目；本机监听不等于安全，不能把能执行命令的服务暴露到局域网或公网。
- 不新增长期配置备份；失败恢复方式沿用已确认的事务安全边界，具体写集与冲突处理另行冻结。
- macOS 与 Windows 分别验证：首次接入、重启、已有配置共存、密钥库锁定、轮换、撤销、取消、重复点击、失败恢复和无秘密泄漏。

这些是后续验收要求，当前未通过运行验证。

## 3. 费用对比不是一张“折扣广告”

### 3.1 两种不同的比较

| 页面 | 用户看到什么 | 数据口径 |
|---|---|---|
| 模型页 | 官网单价 / 我的单价 | 当前模型、账号分组与适用条件；输入、输出、缓存分别显示 |
| 用量页 | 官网同用量估算 / 野菜实际扣费 / 预计节省 | 同一批已经结算的用量；官网是假设按公开价使用的估算，野菜金额来自账单 |
| 明细 | 为什么是这个金额 | 模型 ID、用量分类、单价、条件、价格生效时间、来源与汇率 |

主卡片可突出“预计节省”，但同时显示两边金额、时间范围和比较口径，详情入口叫「怎么算的」。金额条形图必须同零点、同刻度，不能截断坐标或用不同单位夸大视觉差异。

建议短说明：「按相同模型、用量和缓存情况估算，官网美元价格按 6.75 折算；实际扣费以野菜账单为准。」缓存行为在不同平台可能不同，因此不宣称这是用户直接去官网必然收到的账单。

### 3.2 核算原则（提案，待契约与样例验收）

对每一笔可比请求 i：

```text
官网估算 O_i = 当时的官网计费规则（该笔标准化用量、当时适用条件）
              × 已冻结的币种换算系数
野菜扣费 A_i = 该笔最终账单扣费 − 对应退款/冲正
差额 S_i = O_i − A_i

期间 O = Σ O_i，A = Σ A_i，S = O − A
节省比例 = S / O × 100%（仅 O > 0 且同一可比集合时）
```

不能从实际扣费除以一个折扣倍率倒推出官网金额，也不能用总 token 乘一个平均单价。

1. **同一模型和服务条件。** 保留用户请求的完整模型 ID，以及可核实的官网模型/版本映射。不同厂商、别名未解析、不同服务档位或无法确认等价的模型，不硬凑对比。比较的是官网 API 公开计量价，不是订阅月费、企业议价或他人优惠价。
2. **当时的价格，不是今天的价格。** 留存请求时适用的基础价、特殊条件、版本、生效时间及官网来源证据。当前改价不重算旧账；确有纠错时给出新的修订号和原因。旧请求缺少可靠价格历史就标记不能比较，不补造历史价。
3. **完整且不重复的用量。** 区分普通输入、输出、缓存读、缓存写及有效期；不同协议的输入 token 是否包含缓存不能一概而论。已包含在输出中的推理 token 不重复加算。按次、图片、音频、工具调用等有独立费用时分别计量；缺少任何收费维度，就不能假装整笔可比。
4. **适用条件真实。** 长上下文、服务档位、批处理、优惠时段、时区、图片规格等按实际请求条件选择；不能始终选官网最高价。缓存命中也按同一实际用量口径计入，不把所有缓存都按未命中价格计算。
5. **真实结算。** 实际金额来自结算账本，不从客户端价格表预测，不累加预扣与最终扣费，不重复算重试日志。退款、冲正和跨日调整必须关联原账单并以明确的结算截止时间计算。未完成结算的请求显示“结算中”。
6. **扣费不冒充现金支出。** 赠送余额、充值折扣和套餐额度要与现金支付分开。用赠送余额支付仍可显示相应账单扣费，但不能说用户当时付出了等额现金；没有经过确认的套餐分摊规则，不把钱包扣零显示为“免费”或“节省 100%”。
7. **汇率不污染账本。** 6.75 只转换美元官网基准为比较人民币，不乘本站余额或已为人民币的扣费，也不重复转换原本人民币官网价格。不同来源币种/区域价格的选择必须显式记录，不挑较高者；未约定币种不擅自换算。
8. **部分数据就显示部分。** 总计两边必须是相同可比请求集合，并显示“已纳入 x/y 笔”；另列未纳入的扣费和原因。不能拿全账户实际消费与部分官网估算作差，不能把少数可比模型的优惠推广成全站优惠。
9. **负值也如实显示。** 官网估算为零不显示比例；差额为零显示持平，差额为负显示“高于官网估算”，不截成零、不隐藏。不能由于显示两位小数后官网金额变零而产生“无限优惠”。
10. **金额可复核。** 使用十进制定点/整数最小单位和版本化舍入规则，保留计算精度；实际扣费直接保留账本已结算单位，不在客户端重新舍入。官网按规则逐笔计算再汇总，显示时才格式化；如账单采用逐笔舍入，应保留该规则并说明明细合计差异。

### 3.3 可复算的验收例子

以下是**虚构的算式测试数据，不代表任何真实模型价格或当前用户账单**：

- 总输入 1,000,000 tokens，其中缓存命中 800,000；输出 100,000。
- 测试官网单价：未命中输入 $2/百万，缓存命中 $0.20/百万，输出 $10/百万。
- 官网估算：`0.2 × 2 + 0.8 × 0.20 + 0.1 × 10 = $1.56 = ¥10.53`。
- 假设同一笔已结算的野菜扣费 ¥3.00，则预计节省 ¥7.53，比例约 71.5%。

如果错把所有输入都按 $2 计算，就会把官网估算抬高成 $3；这正是必须由测试阻止的夸大。

正式测试还要覆盖：缓存写/读、长上下文边界、优惠时段边界、不同分组、模型别名、改价前后、重复页、重试/退款、赠送与套餐、零/负差额、缺字段、部分覆盖、结算中、跨账号及跨日调整。

本轮用整数算术核对了上述虚构例子的 $1.56、¥10.53、¥7.53 和 71.5%，仅证明示例算式一致，不是计费程序、真实账单或端到端验收通过。

## 4. NewAPI 已有什么，还需要什么

### 已观察到的结构，不能等同当前生产能力

本次读取的是本地上游源码快照 `ac381acf4bf41204b97bb26b4c58c83275877a2e`，并对照公开 GitHub。**它不同于此前服务器审计记录的部署提交，不能据此声称生产字段齐全。**

- `model/log.go:58` 有模型、token 分类、quota、token ID、请求标识和扩展数据；用户日志的展示行号会重排，不能用展示 `id` 作为稳定账单去重键。
- `service/log_info_generate.go:81` 保存部分价格倍率、缓存和模型映射；`:307` 保存阶梯表达式和命中规则。这些可复用，但不能证明每个旧请求都留有完整官网来源、价格历史和收费维度。
- `service/log_info_generate.go:151` 区分钱包与订阅消耗，订阅场景钱包扣费可以为零；这不表示用户没有购买套餐。
- `model/log.go:618` 的汇总固定消费日志，RPM/TPM 另取最近 60 秒；不能直接当作指定期间完整请求数、含退款净消费或官网对比结果。
- `pkg/billingexpr/expr.md` 说明计费表达式与协议相关的用量标准化机制。建议继续由服务端复用计费规则，不在客户端复制表达式解释器。

来源：[账单日志](https://github.com/QuantumNous/new-api/blob/ac381acf4bf41204b97bb26b4c58c83275877a2e/model/log.go)、[费用日志生成](https://github.com/QuantumNous/new-api/blob/ac381acf4bf41204b97bb26b4c58c83275877a2e/service/log_info_generate.go)、[计费规则说明](https://github.com/QuantumNous/new-api/blob/ac381acf4bf41204b97bb26b4c58c83275877a2e/pkg/billingexpr/expr.md)。

现实中的计费条件确实不止输入/输出两个价格，例如当前 [DeepSeek 官方价格页](https://api-docs.deepseek.com/quick_start/pricing/) 区分缓存命中/未命中和高峰/非高峰时段。该页面仅作条件存在的证据，不用于在客户端建立第二张价格表。

### 给技术负责人的增量交接（提案，尚未部署）

在既有 `/api/desktop/v1` 授权和用量投影上补齐，不另设客户端计费数据源：

1. **逐笔结算标识和修订**：稳定账单键、发生时间、结算状态/截止时间、退款冲正关联、账号及工具归因；数据缺失要明确返回，不让客户端猜。
2. **可复核的标准化用量与来源**：模型映射、分类用量、用量是上游报告还是估计、收费维度及适用条件；不能把包含提示词的原始请求或管理员日志直接返回给客户端。
3. **历史官网基准快照**：复用 NewAPI 受控基础价格保存不可变版本、生效时间、来源 URL/核对时间、模型/币种/区域及规则依据。客户端不人工维护另一份数字价表。
4. **实际结算金额和资金类型**：币种/额度单位、净扣费、钱包/赠送/套餐等来源，不能从站点显示货币或倍率猜现金金额。
5. **服务端费用对比投影**：建议扩展 `me/usage` 与 `me/usage-summary`，返回官网估算、实际扣费、差额、可比状态/原因、纳入与排除统计、价格/汇率/算法版本和审计明细。字段名称和闭合 Schema 另行评审，不表示已有接口。
6. **一致的统计范围**：同一账号、时间范围、时区、模型/工具筛选、结算截止点和修订号；退款归属和跨日规则须明确。已有账单页若按入账日期统计，应解释与“请求发生期间”统计的区别。
7. **验收样例**：用普通测试账号提供脱敏请求用量、当时规则、最终账单和对比结果，逐笔及期间汇总对齐后才展示节省；历史不足的模型或日期保持不可比。

已有当前价格投影 `/pricing` 和假设用量 `/pricing/quote` **不能单独替代历史实际费用比较**。

## 5. 下一步及待确认点

- 建议先将 DSH 单列为重点接入入口，并完成固定版本的可视启动和安全凭据方案；不能只增加一张“已支持”的卡片。
- 模型页保留单价对比，用量页增加上述三项费用指标及「怎么算的」。没有真实账单时继续显示不可用，示例只存在于明确标注的测试/设计材料。
- DSH 展示方式已确认：由助手一键启动，在浏览器打开官方本机界面。下一步核对选定发布包、可视启动流程和安全凭据方案；运行环境安装策略、进程生命周期与具体写入契约仍需验证。
- 当前只登记优先级、浏览器打开方式与可审计比较需求。具体适配、数据契约、费用展示规则和验收样例需要形成新的实现单元后才开发，不改写此前冻结单元来扩大权限。
