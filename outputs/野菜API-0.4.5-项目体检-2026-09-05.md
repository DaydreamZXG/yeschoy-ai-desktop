# 野菜API 0.4.5 项目体检

检查日期：2026-09-05。基线：`d1abf2a698c578318a80bc5c0f21d204d9f28c71`。

本报告区分代码观察、隔离复现与优化建议；不把单元测试通过当作真实桌面接入完成。本次没有修改产品行为，也没有修改服务器。线上仅匿名读取两个官方线路的公开价格接口，没有读取真实密钥或代用户调用计费模型。

## 结论

项目已有登录、账户读取、分组计费、配置写入、安全凭据和协议转换的基础，但“登录成功 → 配置成功 → 应用真正使用所选模型 → 退出重开后仍可用”的完整过程尚有断点。建议优先完成可靠性修复与发布验证，再增加客户端种类或嵌入 Agent。

## 优先修复

### F1 · P1 · 登录遇到一次网络错误后不再自动等待授权

证据等级：隔离行为复现。

`src/account/useAccountSession.ts:23` 仅为已登录状态保留旧投影；等待授权时发生网络错误会把状态改成 `network_error`。`src/account/useAccountSession.ts:53` 只在 `authorization_pending` 状态安排下一次轮询，因此后续不再查询授权结果。

隔离复现使用真实 hook、React 与 jsdom，替换网络调用：第一次轮询返回临时网络错误，第二次本可返回登录成功。等待超过两个轮询周期后，调用次数仍为 1，界面仍处于网络错误。这能解释“网站已经确认登录，客户端没有继续反应”的一类原因，但不宣称过去每次故障都由此造成。

建议：授权事务与网络状态分别管理；临时错误保留授权码和截止时间，退避重试；提供继续等待或重新授权的明确入口。取消、切换线路及注销应使旧请求失效，避免迟到的授权结果覆盖新状态。

验收：模拟轮询超时后恢复、授权后首次账户查询失败、轮询期间切线路、取消与成功响应同时发生。

### F2 · P1 · Claude Desktop 的成功判定早于完整回复

证据等级：代码观察。

`src-tauri/src/claude_bridge.rs:289` 在收到上游成功 HTTP 状态后立即发出验证成功事件，此时尚未读取完整正文、完成格式转换或确认流式回复结束。`src-tauri/src/tool_adapters/claude_desktop.rs:306` 收到该事件就返回成功；界面 `src/configuration/ConfigurationPreviewView.tsx:126` 却宣称应用已完成真实回复。

因此，HTTP 200 后接收到错误事件、无效 JSON 或中途断流，仍可能先显示成功。另外，当前验证最多等待应用主动产生请求 90 秒；没有请求不等于配置失败。

Codex 的 0.4.5 验证比此前更明确，但 `src-tauri/src/tool_adapters/codex_desktop.rs:350` 发起的是助手自己的非流式请求，之后才启动桌面应用。它证明所选模型接口可用，不能单独证明 Codex 确实加载了新配置、流式及工具调用均可用。

建议：分别记录配置写入、接口验证、应用加载和真实请求完成。完整回复后才显示“已验证可用”；尚未观察到桌面请求时显示等待验证，并允许重试验证，不将其自动等同于错误配置。

验收：200 后错误事件、空正文、流中断、工具调用再回传、已运行的桌面应用尚未重新加载配置。

### F3 · P1 · 本地转发依赖助手进程，退出后的恢复没有完整产品流程

证据等级：代码观察与生命周期推断。

`src-tauri/src/lib.rs:29` 将 Claude、Codex 的本地转发运行时放在主应用进程内，仅在助手启动时尝试恢复。当前入口未注册托盘、退出协调或独立后台服务。

Claude Desktop 的目标为 `127.0.0.1:15729`；Claude Code 和 Codex 的部分模型也使用本地转发。因此退出助手进程会使这些地址不再提供服务。DSH 的凭据只通过子进程环境注入（`src-tauri/src/tool_adapters/dsh_web.rs:277`），启动入口也没有 DSH 恢复流程。各平台直接关闭窗口是否立即退出进程，仍需安装包实测。

建议：统一后台运行管理和服务健康状态；对依赖转发的应用提供明确的后台驻留与恢复行为；给 DSH 提供安全启动入口。重启电脑后用户应能从助手直接打开应用，不必重复创建令牌、重新配置。

验收：关闭窗口、退出助手、重启助手、重启系统、端口占用、同时打开两个助手实例、DSH 子进程退出后重新打开。

### F4 · P1 · 普通倍率模型的缓存价格被客户端丢弃

证据等级：实时公开接口观察与本机函数演算。

2026-09-05 匿名读取 `https://yeschoy.com/api/pricing` 与 `https://api.yeschoy.com/api/pricing` 均返回成功。全球线路中有 32 条普通倍率计费记录带 `cache_ratio`。例如 `gpt-5.4-nano` 返回 `model_ratio=0.1`、`completion_ratio=6.25`、`cache_ratio=0.1`。

`src-tauri/src/account_v2.rs:1035` 只构造基础输入、输出价格，未投影缓存倍率。`src/configuration/billing.ts:225` 也只生成 `p`、`c` 两项，随后在第 275 行把缺失的缓存价格当作完整输入价格。界面还会声称该模型没有单独缓存价（`src/configuration/BillingGroupPicker.tsx:129`）。

按当前 1 亿 Token 示例，以汇率 1、示例分组倍率 0.16 演算：当前结果为官网参考 30.5、野菜参考 4.88；使用接口已提供的缓存倍率后分别为 16.1、2.576。这里的 0.16 是函数演算示例，不代表此模型对当前账户提供该分组；也未独立核验厂商官网价格，比较仍以用户维护的 NewAPI 基础价为前提。

建议：保留 1 亿 Token 的简洁展示，补齐输入、输出、缓存读取和缓存写入价格字段。仅当服务端确实缺失缓存价格时才使用回退估算。保留价格版本、读取时间和可展开计算说明，模型页与接入页复用同一算法。

验收：ratio 与 tiered_expr 两种计费、零价格、缺失缓存价、多档位、分组切换，以及与后端账单样本核对。

### F5 · P1 · Claude 上游请求没有禁止跨域重定向

证据等级：客户端及锁定依赖代码观察；未发现或模拟真实泄露。

`src-tauri/src/claude_bridge.rs:99` 创建的 HTTP 客户端没有设置重定向策略；第 267 行为原生 Anthropic 请求加入真实 `x-api-key`。

检查当前锁定的 reqwest 0.13.2 源码：默认允许至多 10 次重定向，其跨主机敏感头清理列表包含 `Authorization`、Cookie 等，但不包含 `x-api-key`。若获准上游返回跨域重定向，自定义密钥头可能被带到新地址。已有的初始域名允许列表并未覆盖这种后续跳转。

建议：各转发客户端统一禁止自动重定向，或逐跳验证目标并移除所有凭据头。对错误正文、非流式响应和流式空闲等待也应采用一致的大小及超时限制。

验收：使用假密钥和本地模拟上游验证 301/302/307/308；跨域目标不得收到凭据。无需真实线上密钥。

## 接下来应完善的体验与交付

### F6 · P2 · 首页状态没有与真实配置关联

证据：`src/candidate/CandidateHomeView.tsx:272`、第 276 行固定显示“尚未读取”，第 284 行固定显示“连接状态未确认”。接入结果仅存于配置页的 React 局部状态（`src/configuration/ConfigurationPreviewView.tsx:300`），离开页面会丢失展示依据。

建议：建立每个应用统一的状态记录，包含安装位置、账户归属、模型、分组、线路、配置指纹和最后验证时间；展示时重新读取配置及后台服务状态，区分“之前验证成功”和“当前健康”。首页、接入页、诊断页读取同一记录。只保留必要元数据，不增加用户已否决的长期配置备份历史。

### F7 · P2 · 部分工具完成验证后，用户仍没有可直接使用的入口

证据：Pi（`src-tauri/src/tool_adapters/pi.rs:175`）、Hermes（`src-tauri/src/tool_adapters/hermes.rs:189`）和 OpenClaw（`src-tauri/src/tool_adapters/openclaw.rs:218`）执行一次验证命令后返回；没有对应的持续交互界面启动。当前可调用命令表也没有独立“打开已接入工具”操作。

建议：每个工具都有“安装/打开/修复”入口和清晰的使用形态。已接入后的“打开”不应重复发测试请求、重新写配置。面向小白不要把一次命令行验证完成当作可操作入口交付。

### F8 · P2 · 扫描与模型选择还不够省心

证据：`src-tauri/src/tool_adapters/mod.rs:219` 逐个等待全部工具扫描；单个 CLI 内又逐个等待版本探测（第 144 行），每次上限 8 秒。界面等整个扫描完成后才更新。模型默认值在 `src/configuration/ConfigurationPreviewView.tsx:417` 直接取列表第一项。模型与价格页的应用选择目前仅改变 `tool` 状态，没有用于筛选模型（`src/workbench/ModelsView.tsx:35`）。

建议：有限并发扫描并逐项展示，优先验证用户选中的工具；推荐安装应依据实际 PATH 优先级和明确的应用身份。模型保留完整 ID，增加搜索、最近使用及有依据的推荐说明；分组展示推荐原因和费用，网络线路继续与计费分组分开。

### F9 · P2 · 诊断覆盖不足，缺少可交付给客服的故障证据

证据：`src-tauri/src/connectivity.rs:71` 仅检查 DNS 和 TCP 443，不能定位 TLS、登录、权限、额度、协议转换、模型回复和本地端口的问题。虽然界面有 TCP 范围说明，但用户最常见的接入故障仍无法通过此页查明。

建议：按实际请求路径逐层诊断，提供可复制的错误编号与脱敏报告。基础诊断不产生模型消费；需要模型请求时明确展示。先形成结构化诊断结果，再考虑由 Agent 解释；Agent 不直接拿密钥、执行任意命令或修改任意配置。

### F10 · 发布前必须修复 CI，并完成更新交付

证据：`.github/workflows/ci.yml:63` 仍运行 RU-005 的早期验收。本次本地执行得到 4 项失败，包括已经移除的旧导航、备份栏目和旧扫描调用断言。最新接入、登录及价格修复没有完整进入每次提交的前端检查；主 CI 仍运行较窄的 `test:candidate`。

建议优先修复 CI 的有效验收范围，保留有意义的行为断言，移除已废弃版本的硬编码断言；补齐前面发现的真实失败场景。日常变更按受影响路径测试，发布候选再跑完整平台矩阵，并补齐 Windows 构建缓存，减少反复消耗额度。

`src/candidate/readiness.ts:62` 和 Tauri 配置仍明确关闭自动更新，实际应用没有接入更新插件。仓库继承的 Release 工作流还使用无候选配置的构建命令，而基础配置 `bundle.active=false`；不能把这些旧发布文件当成现成的野菜发布链路。

2026-09-05 只读查看 [Windows 0.4.5 构建](https://github.com/DaydreamZXG/yeschoy-ai-desktop/actions/runs/33884692110)，仍为失败，未有更新的成功构建记录。此前用户截图已证明 Actions 免费分钟耗尽；本次没有改账户预算或重跑付费构建。

建议建立稳定的版本下载页、签名更新清单、应用内更新提示、用户确认后安装和失败恢复。macOS 签名与公证、Windows 当前未签名状态都要在交付记录中如实区分。

## 建议的推进顺序

1. 修复登录重试、Claude 成功判定、跨域重定向和缓存计费；加入能复现故障的行为测试，同时让正式 CI 恢复有效。
2. 建立应用状态读取、后台服务恢复及独立“打开应用”能力，串通首页、配置页和诊断页。
3. 在 macOS Intel、Apple Silicon、Windows 实机上验证“安装 → 登录 → 选择模型/分组 → 接入 → 实际对话/工具调用 → 退出 → 重开”。包括网络错误、权限变化、端口占用及已有配置场景。
4. 完成更新提示与安装交付，再优化推荐、搜索和进阶诊断说明。暂不优先扩充工具数量或让 Agent 代替配置核心。

## 已有基础与保留方向

客户端以原生层管理账户凭据，模型密钥没有直接返回前端；配置写入有快照、原子替换和失败回滚；网络线路与计费分组已分开；协议转换复用了已有转换代码和测试。这些方向可以继续保留，优化重点应放在状态一致性、真实结果验证和安装后的持续可用性。

Codex 当前官方文档确认自定义模型提供商支持 `base_url`、Responses 传输和命令式凭据助手。现有总体配置方向有文档依据，但具体桌面版本是否加载成功仍需实际应用验证。[OpenAI 官方高级配置文档](https://learn.chatgpt.com/zh-Hans/docs/config-file/config-advanced)

本次使用 govern-product-build 的证据分级方式区分了代码、单测、实机与发布验证；没有新建架构门槛或宣称全产品已验收。
