# 野菜 API 桌面助手公开发布整改审计

- 审计日期：2026-09-08
- 候选版本：0.4.15
- 发布单元：RU-074
- 范围：公开版桌面助手、七类客户端接入、本机网关、自动更新、国内下载源、Windows/macOS 发布链路
- 当前结论：仓库内可修复问题已经闭环；在完成签名产物和两套真实系统冒烟测试前，不应把安装包挂到官网。

## 1. 本轮已修复的问题

| 领域 | 原问题 | 当前处理 |
| --- | --- | --- |
| 大请求 | Codex 带图片或长上下文时，本机桥接先缓存请求并在旧上限处返回 413 | 三条 AI 桥接路径统一使用 200 MiB 硬上限；先鉴权，再申请单个大请求槽位，再读取请求体；有 `Content-Length` 时提前拒绝，无该请求头时也在流式读取中执行同一上限 |
| 并发与卡死 | 多个大请求同时进入会抢占内存并让助手看似卡死 | 生产环境只允许一个大请求进入读取阶段；第二个请求立即返回本机 429，不排队、不占用更多请求体内存 |
| 错误归因 | 上游 413/429、上游 5xx 与本机限制容易混为一谈；部分无 `Content-Length` 的失败没有留下记录 | `payload_too_large`、`local_busy`、`upstream_error`、`timeout` 分开记录；Codex、Claude 和通用聊天网关的所有本机溢出路径都会写入“最近连接结果”；上游 413/429 不再伪装成本机错误 |
| 权限 | 助手密钥可能覆盖超出用户所选模型的范围 | NewAPI 助手密钥强制开启模型限制，只绑定本次所选的精确模型和计费分组，并关闭跨分组重试；包含逗号的模型 ID 被拒绝 |
| 密钥轮换 | 修改模型时过早删除旧密钥会把仍在使用的客户端断开 | 新密钥只在本地配置事务提交成功后接管；旧密钥随后回收。失败时回滚本地配置并保留旧密钥可用性 |
| 恢复设置 | 本地恢复完成但远端密钥回收失败时，界面可能误报为全部完成 | 返回“本地已恢复、令牌清理待重试”的独立状态，不要求用户先手工恢复再重新接入 |
| 七类应用 | 修一个客户端容易让另一个客户端出现生命周期或配置差异 | Claude Code、Claude Desktop、Codex Desktop、Pi、DSH web、Hermes、OpenClaw 共用凭据租约、准备/提交/回滚、恢复凭据和取消机制；接入进度可见且可以取消 |
| 正在运行的桌面应用 | Codex/Claude 正在运行时直接改配置，应用继续使用旧配置；助手可能一直等待 | 接入前明确请求用户同意关闭；对 Claude Desktop、Codex Desktop 执行优雅退出并在接入后重新打开；超时和拒绝均有明确结果，不在 UI 线程中无限等待 |
| CLI 应用 | 把 Claude Code、Pi、Hermes、OpenClaw 当成普通 GUI 启动会失败 | 使用可见终端启动；DSH 使用浏览器；所有子进程读取、输出和启动时间均有硬边界 |
| DSH | 启动程序不换行或持续输出时检测长期无响应；“打开使用”无动作 | 启动输出改为有截止时间的有界读取；浏览器打开走系统安全 API，Windows 不再依赖脆弱的命令行猜测 |
| Windows 发现 | 误把 CLI、卸载器或同名文件识别为桌面应用 | 校验 GUI PE 子系统、产品/公司身份和本机 Authenticode；拒绝路径歧义和不可验证的候选程序 |
| Windows 退出/升级 | 关闭窗口后仍留在后台，安装器找不到进程却提示正在运行 | 原生关闭对话框即使 WebView2 页面加载失败也能工作；安装器使用命名事件请求安全退出，二次确认后只按已解析出的精确 PID 强制结束，中文安装提示已配置 |
| 自动更新 | 设置页显示不支持，回到应用后不检查；快速双击可能提交两次安装 | 使用固定 HTTPS 更新清单；启动及从后台返回（最短五分钟间隔）检查；网络回复 15 秒截止；安装阶段使用同步状态门，第二次点击立即被拒绝 |
| 下载与发布 | 只验证清单存在，安装文件即使公开地址为 404 也可能被当成发布成功 | 候选构建和正式推广分离；公开探测会检查更新清单、官网安装清单以及每个产物的 HTTPS 地址、Range 响应、`Content-Range` 和安装文件总大小；失败触发现有 CAS 回滚 |
| 降级 | 暂停自动更新后可能把更老版本重新发布为稳定版 | 更新清单和官网安装清单分别执行单调版本检查；删除更新清单不会绕过官网安装清单的版本保护 |
| 供应链 | 工作流依赖浮动 action、旧依赖漏洞、签名检查不足 | GitHub Actions 全部固定到提交；候选流程执行依赖审计、Windows Authenticode、macOS Developer ID/公证/Gatekeeper 校验；正式推广还会复核候选仓库、提交、文件哈希和 minisign 签名 |
| 安装能力表述 | “一键安装”覆盖范围写得比真实能力大 | 只有当前已验证的 Claude Desktop 与 Codex Desktop 可标为自动安装；CLI 客户端显示“官方安装指引”；所有镜像产物安装前必须校验厂商身份与签名 |
| UI/UX | “重新接入”不明显、错误只给结论、语言完成度和发布状态容易误导 | 接入成为明确的可重试状态机；展示进度、取消、重试、恢复和最近错误；简体中文标注完整，其他语言明确标注部分覆盖；候选状态不再宣称生产就绪 |
| 模型显示 | Claude/Codex 可能显示静态品牌名，模型与思考强度不一致 | 路由保留实际上游模型 ID；已知 GPT、Claude、DeepSeek 等家族统一显示规则并按模型能力裁剪思考强度；旧 Claude 别名只作为迁移兼容，不再发送不存在的路由 ID |

## 2. 关键设计边界

1. 本机回环服务只监听本机地址，客户端只拿最小范围临时密钥。鉴权发生在大请求体读取之前。
2. 200 MiB 是防止失控内存占用的硬上限，不是承诺所有上游都接受 200 MiB。上游自己的上下文、图片和网关限制仍可能更小，届时会按上游错误展示。
3. 接入事务的顺序是：检查应用状态与用户同意 → 准备密钥和配置 → 安全写入 → 验证 → 提交 → 必要时重启目标应用。失败时按恢复凭据回滚。
4. 自动更新产物与官网安装包采用同一版本，但使用各自清单；两份可变清单都受版本单调性和 CAS 回滚保护。
5. 朋友定制版 `ai.yeschoy.io` 只改变 OAuth 登录确认页品牌/回跳入口；API、模型、计费和公共实现仍复用主版本。它必须使用独立签名产物与更新清单，不能让两个品牌相互覆盖升级。
6. 厂商安装包同步任务只生成私有候选和验证证据，不会自动向公网发布。最终发布必须是显式的运营操作。

## 4. 上官网前仍需完成的外部发布门槛

以下项目依赖真实证书、平台或公网环境，代码仓库无法用模拟测试替代：

1. 由受保护的候选工作流生成 Windows x86_64 签名安装包；在干净 Windows 机器验证首次安装、中文界面、WebView2 缺失/页面失败时退出、后台退出、覆盖升级、Codex/Claude 正在运行时接入。
2. 生成 macOS Universal 包，完成 Developer ID 签名、Apple 公证和 stapler；分别在 Intel 与 Apple Silicon 的干净账户下验证 Gatekeeper、首次启动、接入、恢复和升级。
3. 使用真实 Tauri updater 私钥生成签名，保持私钥只在受保护 CI 环境中；确认候选产物的哈希、签名和版本与清单完全一致。
4. 通过受保护的正式推广流程发布到 `ergou.qzz.io`，检查公网 TLS、完整下载、Range 请求、更新清单、官网安装清单、应用内更新和一次真实回滚演练。
5. 若同时发布朋友定制版，为其建立独立 bundle identifier、签名身份、安装文件名和更新通道，并验证它不会覆盖主版本。

完成以上 1–4 后，主版本才适合在官网公开下载。第 5 项只在朋友版同步发布时需要。

## 5. 已知但不阻塞本轮候选的事项

- Renderer 主包仍大于 1 MiB，可在后续用路由/功能懒加载拆分；这影响首次渲染效率，不影响当前正确性。
- 仓库里还有未进入公开发布面的 CC Switch 历史实现和文档。公开工作流、更新清单、安全说明和下载源已移除其身份；彻底删除应单独做依赖闭包审计，避免误伤仍复用的适配逻辑。
- RustSec 的 18 个警告主要位于当前未发布的 Linux/Tauri GTK3 依赖树和传递依赖。Windows/macOS 候选不因此放行漏洞，但后续升级 Tauri 依赖时应持续复核。
- 浏览器模拟环境仍会输出少量元数据/布局警告；现有断言通过，可作为测试噪声治理项单独处理。
