## 0. 先看这一条：兼容闸门已经整个撤掉，不要装回去

这是本轮最大的改动，也是最容易被好心改回去的一条。

以前 `modelCompatibility.ts` + `tool_activation.rs` 有一道闸门，按 `/api/pricing` 的 `supported_endpoint_types` 判断"这个模型能不能在这个应用里用"，不能的就置灰。**它连续判错四次，而且每次都是同一个方向 —— 把"我们不知道"当成"它不行"：**

1. 按 `openai` / `openai-response` 的差别置灰 —— 这两个的区别根本不是能不能用。
2. 改成"没有价目行就不能用" —— `/api/pricing` 只覆盖它定过价的模型，账号可用列表里还有别的（线上就有 `deepseek-v4-flash`），于是能跑的模型被挂上"哪个应用都用不了"。
3. 改成"端点列表为空就不能用" —— 中转查不到模型时返回的也是空切片，和"真的零端点"是同一个值，分不开。
4. 每次"修好"都只是把线往后挪，因为线本身就不该存在。

**根因：没有可靠信号。** 产品负责人的原话是"我感觉我们没办法控制"，这是对的。于是 `1b3fb135` 把闸门整个撤掉：每个模型在每个应用里都能选，不藏、不灰、没有任何"用不了"的话。真不能用的，中转会返回明确报错 —— 那比我们拿一个不可靠的字段提前替用户判死要诚实。

**要重开闸之前，先读 `src/configuration/modelCompatibility.ts` 顶部的注释块。** 那里完整保存了查证过的中转事实，不用重新推一遍。结论是：唯一有证据支撑的限制只有"Codex + 纯 Anthropic 渠道的模型"，而且那条会随中转升级失效。

## 1. 中转是 fork，不是上游 —— 这一条坑过我

野菜部署的是 **`github.com/yeschoy/new-api`**（公开仓库，可直接 clone 读），**不是** `QuantumNous/new-api@main`。两者在关键处不一样：

| | 上游 main | 野菜部署的 fork |
| --- | --- | --- |
| claude adaptor 的 `ConvertOpenAIResponsesRequest` | 有真实现 | `return nil, errors.New("not implemented")` |

我曾按上游放开了"Codex 可以用 Anthropic 渠道的模型"（`f8e9fb2d`），随后按 fork 改回（`b7eb7b6f`）。**任何关于中转行为的判断，都要对着那个 fork 读，不要读上游。**

已查证并写进注释的事实（都在 fork 上复核过）：

- `supported_endpoint_types` 由 `common/endpoint_type.go` 按**渠道类型**算出，在 `relay/` 全路径下零引用，只被两个展示用 controller 读。**它不是准入白名单。**
- `GetModelSupportEndpointTypes` 查不到模型时返回空切片，与"真的零端点"同值，外部分不开。
- 有 ability 的模型至少有一个端点（`GetEndpointTypesByChannelType` 兜底返回 `[openai]`），所以**空列表只能是"没查到"**。
- `/v1/messages` 打到任何渠道都行；openai adaptor 里"只有 claude 模型才让转"的守卫是被注释掉的。
- `/v1/chat/completions` 打到 Anthropic 渠道也行（claude adaptor 的 `ConvertOpenAIRequest` 有真实现）。

**中转代码不归我们改。** 运营方明确拒绝过代码推送，只接受改配置。客户端侧解决。

## 5. 未完成 / 需要决策的

**(a) 接入页还差步骤编号。** 现在是「1 模型 / 2 价格 / 3 完成接入」，设计稿是「1 应用 / 2 模型+价格 / 3 完成接入」。这是纯视觉调整，我故意留着 —— 在看不到界面的情况下改编号是对着想象调。产品负责人手上有设计稿截图。

**(b) Claude Desktop 的自动压缩，没有验证。** 查证过程和结论：

- Desktop 的 `inferenceModels` 每一项**没有上下文窗口字段**。schema（从安装包 `app.asar` 里拆出来的）给每项：name、display name、`supports1m`、`prefer1m`、`anthropicFamilyTier`、`isFamilyDefault`、`maxEffort`。**所以 profile 这条路走不通，不用再试。**
- `~/.claude/settings.json` 里有 `autoCompactWindow` 和 `contextWindowByModel: Map<string, number>`，查找时会剥掉结尾的 `[1m]` 再查一次。但那个文件是 Claude Code 的，**Desktop 的聊天界面读不读它无法确认**。
- 最后选的做法（`1f4f136f`）：不猜别人的私有配置键，改成在**我们自己拥有的接口**上说对 —— 桥的 `/v1/models` 报出窗口。Desktop 会做 dynamic discovery（其 schema 原话 "the first model your endpoint returns under discovery"）。三个键的出处：`max_input_tokens`/`max_tokens` 是 Models API 标准字段，`max_output_tokens` 是 Desktop 自己内置目录的拼法。

  **代价结构变了**：以前是"猜对才有用、猜错可能弄坏用户配置"，现在是"读了就有用、不读也没损失"。但**有用与否仍未验证**。

  要继续查的话：`~/Library/Application Support/Claude-3p/configLibrary/00000000-0000-4000-8000-000000157220.json` 是我们写的 profile，Desktop 日志能看到它有没有打 `/v1/models`。

**(c) `codex-auto-review` 在目录里没有能力资料。** 它是服务端路由别名，找不到可引用的来源，所以留空。`hasReviewedCapabilities()` 会让它不当默认值，但选中时卡片上没有标注。有来源的话补进 `src/model-profiles/catalog.json`。

**(d) 中转侧自相矛盾（不归我们修）：** `gemini-3.1-pro-low` 在 `/api/pricing` 里有 `model_ratio: 37.5`、两个分组都开着，请求却返回"价格尚未由管理员配置"。

## 6. 模型目录已经上线了

`https://ergou.qzz.io/apps/model-catalog.json`（+ `.sha256`），落在 `/srv/yeschoy-download/public/apps/`。

原来代码里指向 `https://yeschoy.com/desktop/model-catalog.json`，**那个路径从来没部署过** —— 主站是 SPA，未知路径返回 200 + HTML，所以客户端每次启动都静默走 `invalid_payload` 兜底，功能上线以来一直没生效过。

下载源的 Caddy 是白名单式的（只放行 `/apps`、`/releases`、`/updates/releases` 等），`/apps/` 已在名单内，**所以挂这里不用改服务器配置**。

以后上新模型：改 `src/model-profiles/catalog.json` 里的 `verifiedAt`，然后

```bash
node scripts/ops/publish-model-catalog.mjs --to /srv/yeschoy-download/public/apps
```

脚本会先校验再写，走临时文件 + rename，读者不会看到半个文件。客户端只在 sha256、schema、`verifiedAt` 三关都过且严格更新时才采用。

## 7. 给接手者的几句实话

本轮我犯的错集中在一个模式上：**把"不知道"当成"不行"**，前后三次（端点差别、缺价目行、空列表），每次都是在没有可靠信号的地方做了确定性判断。现在代码注释和测试把这条原则钉住了 —— 要收紧任何闸门，先拿出明确的声明，而不是一个空位。

另一个：**改行为之前先 grep 断言旧行为的测试。** 这一轮有四次是测试先拦住我的，包括 Workbench 里那条"Codex 下 anthropic-only 模型无兼容模型"的断言 —— 它是对的，我改错了。

环境上：这台 Linux 机器可以装 node 和 rust（`apt-get install libwebkit2gtk-4.1-dev libsoup-3.0-dev ...` + rustup 1.95），前面几轮"编译不了"的说法是错的，别被旧记录误导。
