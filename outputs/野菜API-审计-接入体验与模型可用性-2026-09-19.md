## 1. 启动外部应用：失败原因在 Rust 侧就被丢掉了

**已验证。** 这直接对应你报的第二个症状，也直接违反任务书验收「所有失败状态都有明确下一步」。

### 1.1 日常「打开使用」路径：全部失败塌缩成一句话

`src-tauri/src/open_connection.rs` 用 `.map_err(|_| "launch_failed")` 丢弃整个 `AdapterFailure`（第 201、223、251 行）。`OpenResponse` 只有 4 个字段（`request_id` / `schema_version` / `tool_id` / `status`），**没有 reason code 通道**；`src/configuration/launchApi.ts` 还用 `Object.keys(value).length !== 4` 把这个契约锁死。

于是不论真实原因是工作区目录没了、终端起不来、应用拒绝退出还是权限被拒，用户永远只看到：

> 没能打开应用或终端。请确认应用可以手动打开、未被系统阻止，再重新检查。

### 1.2 接入路径：4 个真实原因码没有对应文案

`ConfigurationPreviewView.tsx:953-971` 的 `launch_failed` 分支只映射了 6 个原因码。Rust 实际会发出但**前端零引用**的有：

| 原因码 | Rust 发出处 | 前端引用数 |
| --- | --- | --- |
| `terminal_launch_failed` | `terminal_launch.rs`，**13 处** | 0 |
| `desktop_launch_activation_failed` | `desktop_launch.rs` | 0 |
| `desktop_launch_exit_failed` | `desktop_launch.rs` | 0 |
| `desktop_launch_wait_failed` | `desktop_launch.rs` | 0 |

全部落到通用文案「设置已经保存，但没有自动打开应用。**请手动打开**；不需要重新接入。」

其中 `terminal_launch_failed` 最要命：它是 Claude Code 和 Pi 的启动路径（13 处触发点），而这两个是**终端工具**——让用户「手动打开应用」是错的建议，助手的价值恰恰是替他把带正确参数的终端拉起来。

### 1.3 反向：前端映射了 Rust 永不发出的原因码

- `desktop_launch_identity_invalid`（`ConfigurationPreviewView.tsx:963`）——Rust 侧 0 引用
- `unsupported_group` / `g.unsupportedGroup`——`b7cdaea3` 撤掉分组闸门后，`ActivationFailure::UnsupportedGroup` 已成死变体（cargo 编译警告实证：`variant UnsupportedGroup is never constructed`）

## 2. 远程模型目录被应用自己的 CSP 挡死

**已验证，且是本轮新发现（任何交接文档都没提）。**

`src-tauri/tauri.conf.json:30` 的 CSP：

```
connect-src 'self' ipc: http://ipc.localhost
```

`src/model-profiles/remoteCatalog.ts:160` 用**渲染层的普通 `fetch()`** 去取 `https://ergou.qzz.io/apps/model-catalog.json`。该源不在 `connect-src` 白名单里，请求必被拦截，`refreshModelCatalog()` 永远返回 `{status:"bundled", reason:"fetch_failed"}`。

浏览器中实测到的拦截（同一份渲染代码）：

```
Access to fetch at 'https://ergou.qzz.io/apps/model-catalog.json'
blocked by CORS policy / net::ERR_FAILED
```

**对照证据：** 同一个域名在 Rust 侧用得好好的——`update_channel.rs`（更新通道）、`app_installation/origins.rs:12`（应用安装目录 `CATALOG_URL`）。**模型目录是唯一一处从渲染层直接取外部资源的**，也是唯一一处被 CSP 挡住的。

交接文档说这个功能「一直没生效过」是因为 URL 没部署，`abcb602f` 改了 URL。**但 URL 不是唯一的堵点**——CSP 从来没开过这个源。功能至今仍未生效。

影响：模型显示名、上下文窗口、推理档位等能力元数据永远停留在打包时的 `catalog.json`，上新模型必须发版。

### 2.1 这不是后台哑功能，它在主选择器上有可见后果

同一次实机验证里，四个模型在选择器中呈现为**两个视觉等级**：

- `glm-5.3` → 「GLM-5.3」+ 徽章「1M 上下文 · 思考 none·low·high·max · 工具调用 · 最大输出 131.1K」
- `deepseek-v4-flash` → 「DeepSeek V4 Flash」+ 完整徽章
- `gpt-5.6-codex` → **只有一行等宽小字 `gpt-5.6-codex`，无显示名、无任何徽章**
- `claude-sonnet-4-5-20250929` → 同上，裸 ID

原因已核：`src/model-profiles/catalog.json` 收录 75 个模型，前两个在内、后两个不在。

**所以链条是完整的：CSP 挡住远程目录 → 目录只能随版本更新 → 任何未打包进目录的模型在选择器里都退化成一行裸 ID → 一个专门服务「不会配置的人」的产品，让用户在「GLM-5.3 · 1M 上下文」和 `gpt-5.6-codex` 之间做选择。** 上新模型必须发版这件事，代价直接落在主流程的核心控件上。

**建议修法：** 参照 `app_installation/origins.rs` 的既有做法，把这次取数挪到 Rust 侧（顺带获得证书校验与统一超时），而不是放宽 CSP。

## 3. 成功状态只有一级，且在写完配置时就放礼花

**已验证。** 任务书的第一号要求是把成功拆成「配置已完成」与「首次使用已验证」两级。现状：

`ConfigurationPreviewView.tsx:2213-2235` 的成功标题只取决于 `activationSucceeded` / `resultIsCurrent` / `firstActivationCelebration`——**没有任何一项涉及真实请求观测**。配置写入成功即显示「第一次接入成功」并触发 `CelebrationConfetti`。

## 3.1 Claude 为什么不自动压缩：同一个目录陈旧问题的第三个后果

**已验证。** 这是本轮追加的问题，结论和 §2 同源。

Claude Code 的自动压缩由 `~/.claude/settings.json` 的 `autoCompactWindow` 驱动，值来自 `tool_adapters/claude_code.rs:71` 的 `auto_compact_window()`：

```rust
let window = crate::tool_model_profile::profile(bare)?.context_window?;
```

**模型不在目录里 → 返回 `None` → 这一项被主动删除 → Claude Code 不知道窗口有多大 → 不会自动压缩。** 代码注释自己写清楚了后果：

> 结果就是对话涨过窗口也不会自动压缩，一直涨到中转那边报上下文超限，用户看到的是一条报错而不是一次压缩。

而这个目录在 Rust 侧是**编译期内嵌**的：

```rust
// tool_model_profile.rs:212
serde_json::from_str(include_str!("../../src/model-profiles/catalog.json"))
```

实测数据：目录共 75 个模型，**全部 75 个都有 `contextWindow` 且都 ≥ 100000**，也就是说凡在目录里的模型都会写入 `autoCompactWindow`。失败场景只有一种 —— **模型不在目录里**。

更关键的是：**远程目录刷新即使修好了也救不了这件事。** `applyModelCatalogOverride()` 只替换渲染层 `profile.ts` 里的 Map，全部调用方都在渲染层，没有任何 IPC 把它送到 Rust。Rust 那份是 `include_str!`，**只能靠发版更新**。

所以「Claude 没办法自动压缩」的准确表述是：**目录里那 75 个模型会自动压缩；此外的任何模型都不会，而且只能等下一个版本。** 和 §2.1 的裸 ID 是同一个根因的两个面。

## 4. 接入页：三步只画出两步，第三步被 CSS 藏掉了

**已实机验证（浏览器渲染 + DOM 实测）。**

`ConfigurationPreviewView.tsx` 渲染了三个 `.choice-number`，但实测它们的可见性是：

| 行号 | 编号 | 归属标题 | 实际可见 |
| --- | --- | --- | --- |
| 1757 | 1 | 选择模型 | ✅ 24×24 |
| 1843 | 2 | 选择价格方案 | ✅ 24×24 |
| 1999 | 3 | 完成接入 | ❌ **0×0，`display: none`** |

肇因是一条 CSS：

```css
/* src/workbench/workbench-v2.css:6275 */
.connection-summary-intro .choice-number {
  display: none;
}
```

**于是页面承诺了一个编号序列，画出 1 和 2，然后在承载主操作（「一键接入」）的那一步悄悄断掉。** 这比单纯的「编号该从应用算起」更严重：它不是顺序错，是序列残缺。

实测标题顺序（DOM）：

```
选择模型(1) → 选择价格方案(2) → 常用模型(无编号) → 完成接入(3，不可见)
```

即第 2 步和第 3 步之间还插着一个无编号的「常用模型」区块。加上最上方同样无编号的应用选择卡片，**一个自称三步的页面上实际有 5 个同级区块，其中 3 个没有编号。**

另：三个编号都带 `aria-hidden="true"`，也没有 `aria-posinset` / `setsize` 或有序列表语义，屏幕阅读器完全拿不到步骤结构。任务书要求「屏幕阅读器语义」。

设计稿要求 `1 应用 / 2 模型+价格 / 3 完成接入`（交接文档 §5(a)），与现状差两层。

### 4.1 同一页上有 8 个折叠区

DOM 实测 `<details>` 清单：安装与接入信息、计费详情 ×3、每百万 tokens、1 亿 Token 费用参考、查看连接详情、网络线路。任务书验收明确把「关键操作藏在不可发现的折叠区中」列为失败条件。

### 4.2 「最近野菜中转记录」在尚未接入时就出现

未接入状态下该面板已渲染，内容是「尚未收到该应用经野菜中转的请求」，下面跟着一段工程口径的说明：「记录来自服务端用量日志，按该工具自己的密钥归因，显示实际转发的完整模型 ID；不依据应用错写或 AI 的自我介绍判断。」——对新手既是噪声也是术语。

但这正是 §3 两级成功状态的证据面板，重构时应该**从「一直显示的空面板」改成「配置完成后的等待验证态」**。

## 6. 布局：横向不溢出（此前的担心可以排除），问题在纵向

**已实机验证，并修正了我先前基于数值的推测。**

- 窗口默认 `1120×760`，最小 `860×640`（`src-tauri/tauri.conf.json`）
- 接入页内容容器 `max-width: 940px`（`workbench-v2.css:5513`）
- 全文件仅 5 个 `@media` 断点

**结论：在 860 最小宽度下没有横向溢出、没有横向滚动条、没有控件重叠。** `max-width` 会自然收缩，我此前「940 放不下 860」的推断是错的——那是 `max-width` 不是 `width`。浅色与深色两套主题在 860 与 1120 两种宽度下都渲染正常，对比度正常。

**真正的问题是纵向：** 在默认 `1120×760` 下，首屏只能看到到「② 选择价格方案」的标题；在最小 `860×640` 下，首屏只能看到「① 选择模型」。**承载主操作的「一键接入」按钮在两种尺寸下都在首屏之外**，页面也没有任何进度指示告诉用户还剩多少。这与任务书「每个页面应有一个明确的主要动作」直接冲突。

### 6.1 一个方法学提醒（给后续做视觉验收的人）

浏览器窗格的截图在**滚动之后**会出现约 450px 的合成偏移：截图里侧边栏和内容整体下移、顶部留出大片空白，但 DOM 实测 `sidebarTop = 0`、`step2Top = 152`、`visualViewport.offsetTop = 0`。**这是截图工具的合成问题，不是应用缺陷。** 我先后两次差点把它记成布局 bug。

可靠做法：不要滚动，改用超高视口（如 `1120×1900`）一次性渲染整页；或者用 DOM 量测代替肉眼判断。

# 附录 A：实施后的更正（2026-09-20）

动手改的过程中，有四条审计结论被证伪或高估。留在这里，比悄悄改掉诚实。

### A.1 「三份译文已打包进产物」—— 错

`en/ja/zh-TW` 三个文件**根本不进构建产物**。Vite 只打包被 import 的模块，而
`src/i18n/index.ts` 只 import 了 `zh.json`。实测 `pnpm build:renderer` 后在
`dist/` 里 grep `Sign in` / `ログイン` / `登錄` 全部无命中。

所以代价只是仓库里 ~58KB 的冗余和长期漂移风险，**不是发布体积，也不是加载问题**。
要不要删，取决于还要不要做非中文市场 —— 那是产品决策，不是工程缺陷，没有动。

### A.2 「ModelsView / 诊断页 / 工具页是死胡同」—— 错

侧边栏 (`WorkbenchSidebar`) 渲染在 `App.tsx` 的外层壳里，**包住所有视图**，
任何页面都随时能一键去别处。不存在出不去的页面。

### A.3 「侧边栏在这三个视图上错误高亮设置」—— 错，那是有意的

`WorkbenchChrome.tsx:106-109` 有明确注释：模型与价格、连接诊断、已安装的工具
是设置页的子页面，不是顶级目的地，所以高亮到设置上 —— 而这个高亮**正是**用户
回去的路。没有动。

### A.4 「缺少 onboarding，第一次打开和第一百次一样」—— 高估了

实机看过未登录首屏：有「野菜 API · 你的 AI 工作台」、有「选一个应用，安装并连接
你想用的模型」、有一条醒目的登录条（唯一的实心主按钮），六张应用卡片的「开始接入」
是次级文字链。视觉层级是对的，任务书第 1 步（进入即理解产品能做什么、下一步是
什么）基本满足。

未登录态在实践中就是首次运行态。再加一个向导页，会把真正有价值的东西（应用列表）
推到一屏之后，也与产品自己的设计原则相悖。**没有建 onboarding 页**；如果你认为
仍然需要，这是个值得单独讨论的产品决定。
