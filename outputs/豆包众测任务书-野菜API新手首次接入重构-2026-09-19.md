# Coding 众测任务：重构野菜 API 桌面助手的新手首次接入体验

## 背景

野菜 API 桌面助手是一个 Tauri 2 + React + Rust 桌面客户端，帮助不会手工修改配置的用户安装、接入和恢复 Claude Desktop、Codex Desktop、Claude Code、WorkBuddy、Pi、DSH web 等 AI 工具。

当前产品已经具备账户登录、应用发现与安装、模型和计费分组选择、安全配置写入、原设置恢复、连接诊断、退出恢复和自动更新等能力，但首次使用流程仍然让新用户难以判断：下一步应该做什么、配置是否真的生效、应用是否需要新建窗口，以及一次失败之后如何继续。

请基于附件仓库完成一次真实、可运行、可验证的产品级重构。基线提交必须是：

`c5dc1f2924af3d116c1033e4c30ab5f5b37fda79`

## 核心目标

重构“小白用户从打开助手，到在目标 AI 应用中完成第一次真实成功请求”的完整旅程，同时重构相关页面的信息架构、交互反馈和 UI 视觉系统。

新版必须把成功状态分成两个层级：

1. **配置已完成**：配置事务、安全存储、配置回读和必要的应用启动步骤已完成。此状态不能声称模型请求已经成功。
2. **首次使用已验证**：用户自行在目标应用发送真实请求，助手从已有请求诊断或连接观察中取得成功证据后，才允许显示最终成功状态。

客户端不得为了验证而自动发送可能计费的模型请求。

## 必须完成的用户旅程

围绕一个新手用户，重新设计并实现以下连续旅程：

1. 进入助手后，立即理解这个产品能做什么以及当前下一步。
2. 选择一个目标应用；若未安装，能够理解并完成安装或获取明确的替代动作。
3. 在需要时完成账户登录，并看到可信的账户、模型和价格状态。
4. 选择模型与计费分组，不因缺失或不可靠的协议元数据隐藏、置灰模型或分组。
5. 清楚理解即将修改什么、不会修改什么，再执行接入。
6. 在接入过程中看到真实、稳定、可恢复的进度；不能用循环动画掩盖无进展状态。
7. 配置成功后进入“等待首次验证”，引导用户打开目标应用并发送第一条消息。
8. 观察到真实成功请求后进入“首次使用已验证”，显示实际应用、模型、线路、时间等证据。
9. 请求失败时提供与错误类型匹配的下一步操作；用户可以重试、调整配置、恢复原设置或稍后继续。
10. 关闭、重启、取消、网络中断或应用仍使用旧窗口时，流程能够恢复，且不会伪造完成状态。

## UI 与交互要求

- 允许重新规划现有导航和页面层级，但必须保留账户、用量账单、设置、诊断和恢复能力。
- 以新手任务为中心，不以工程模块或配置文件为中心。
- 删除重复标题、重复说明、套娃卡片和同时争夺注意力的主按钮。
- 每个页面应有一个明确的主要动作；次要、危险和恢复动作需要清楚区分。
- 建立一致的颜色、字体、间距、表单、按钮、提示、进度和状态视觉语言。
- 同时支持浅色和深色主题。
- 支持较窄桌面窗口、长中文、键盘操作、可见焦点、屏幕阅读器语义和系统减少动效设置。
- 动效必须表达状态变化或空间关系；不能用装饰动画代替状态证据。
- 不得使用营销落地页式的巨大 Hero、无意义渐变、装饰性色块或多层卡片套娃。
- 在 macOS 与 Windows 的普通桌面窗口尺寸下，主要内容不能溢出、遮挡或依赖横向滚动。

## 必须保留的产品与安全边界

- 保留现有 6 个已支持应用及其真实配置适配器。
- 保留事务式配置写入、冲突检测、失败回滚和恢复原设置能力。
- 不得将 WorkBuddy 改成本地网关方案。
- 不得静默覆盖用户在助手之外进行的配置修改。
- 不得强制结束目标应用进程。
- 不得把“应用已经打开”“配置文件已经写入”描述成“模型调用成功”。
- 不得恢复已经撤除的模型或计费分组兼容门禁。
- 不得改变服务端 API、价格算法、账户余额算法或线上发布基础设施，除非现有客户端契约无法实现目标；发现这种情况应记录为阻塞，不得自行发明服务端行为。
- 不得读取、记录或展示明文密钥。
- 不得修改版本号、上传服务器、发布安装包或推送远端。

## 关键异常场景

至少覆盖并验证：

- 应用未安装、发现失败、发现多个安装副本。
- 未登录、会话过期、账户接口暂时不可用。
- 模型或计费分组数据缺失、刷新失败、保存的模型已经下线。
- 接入过程中取消、超时、客户端关闭或应用拒绝退出。
- 配置写入成功但应用启动失败。
- 配置完成后用户继续使用旧窗口，真实请求仍走旧配置。
- 首次请求出现 401/403、429、未知模型、上下文过长、网络错误、上游错误或流中断。
- 用户在助手之外修改配置，导致读取结果和已保存收据冲突。
- 退出时选择后台运行、保留设置退出或恢复原设置退出。

## 验收标准

### 功能

- 新手能够沿一条连续主路径完成“选择应用 → 登录 → 选择模型/价格 → 配置 → 打开应用 → 发送第一条消息 → 验证成功”。
- “配置已完成”和“首次使用已验证”具有不同、可测试的状态及文案。
- 最终成功必须包含真实请求观察证据；没有证据时不能显示最终成功。
- 所有失败状态都有明确下一步，并能在刷新、返回、重启后保持诚实状态。
- 现有已接入用户仍能打开应用、更换模型、查看账单、诊断和恢复设置。

### 工程

- 不得通过删除现有测试、弱化断言、写死测试夹具或跳过 Rust/TypeScript 校验来通过验收。
- 为新增状态和关键异常路径补充自动化测试。
- 至少运行并报告：
  - `pnpm typecheck`
  - `pnpm test:unit`
  - `cd src-tauri && cargo test --lib`
- 如果全仓已有与本任务无关的格式问题，需要区分既有问题和本次新增问题，不能擅自批量格式化无关文件。

### 视觉与可用性

- 提供新手主流程在浅色和深色主题下的实际截图。
- 至少检查宽窗口与窄窗口两种桌面尺寸。
- 页面没有文字截断、控件重叠、不可见焦点、低对比度或关键操作藏在不可发现的折叠区中。
- 尊重 `prefers-reduced-motion`。

## 交付内容

1. 可运行的代码修改。
2. 修改文件清单和关键设计说明。
3. 新旧用户旅程对比。
4. 状态模型及异常恢复说明。
5. 自动化测试命令和精确结果。
6. 浅色/深色、宽/窄窗口截图。
7. 未解决问题、假设和风险，不得把未验证事项描述为已经完成。

## 工作方式

- 先审计现有代码、测试和状态契约，再决定实现方案。
- 可以调整实现设计，但不得偏离上述目标和边界。
- 发现契约冲突或需要破坏兼容性的改动时应停止该部分实现，明确报告证据和建议，不得用临时绕过掩盖问题。
- 最终只提交候选实现和验证证据，不得推送远端或部署生产环境。
